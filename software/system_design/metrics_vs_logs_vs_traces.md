# Observability in Distributed Systems: Metrics, Logs, and Traces

Understanding what’s happening in a modern distributed system requires **observability**, which includes **metrics, logs, and traces**. so, let’s clarify them using a consistent example:

### **Example Business Process:**

Imagine an **e-commerce order processing workflow** implemented as microservices:

1. **API Gateway** receives the order request.
2. **Order Service** validates the order and stores it in the database.
3. **Payment Service** charges the customer.
4. **Inventory Service** updates stock.
5. **Notification Service** sends confirmation email/SMS.

We’ll see how **metrics, logs, and traces** capture different aspects of this workflow.

---

## 1. Metrics

**Definition:**
Metrics are **numerical measurements over time** that represent the health or performance of your system. They are often aggregated, monitored, and used to trigger alerts.

**Characteristics:**

* Quantitative and time-series data.
* High-level view, often aggregated across many requests.
* Useful for monitoring trends and triggering automated actions.

**Example Metrics in Our Workflow:**

| Metric                  | Description                       | Value / Unit   |
| ----------------------- | --------------------------------- | -------------- |
| `orders_received_total` | Total orders processed per minute | 150 orders/min |
| `payment_failures`      | Number of failed payments         | 3 failures     |
| `order_latency`         | Time taken to process an order    | 450 ms         |
| `inventory_low_alerts`  | Stock alerts triggered            | 2 alerts       |

**Key point:** Metrics **don’t contain detailed info about individual requests** — they give an overview of system health and performance.

---

## 2. Logs

**Definition:**
Logs are **time-stamped records of discrete events**. They capture **what happened** in a specific service.

**Characteristics:**

* Event-oriented (errors, warnings, info).
* Can be structured (JSON, key-value) or unstructured (text).
* Usually generated by each microservice.

**Example Logs in Our Workflow:**

**Order Service:**

```json
{
  "timestamp": "2025-09-28T09:00:05Z",
  "level": "INFO",
  "service": "order-service",
  "message": "Order 12345 validated successfully"
}
```

**Payment Service:**

```json
{
  "timestamp": "2025-09-28T09:00:06Z",
  "level": "ERROR",
  "service": "payment-service",
  "message": "Payment failed for order 12345",
  "errorCode": "CARD_DECLINED"
}
```

**Key point:** Logs show **what happened at a particular point in a service**, but don’t inherently connect multiple services together.

---

## 3. Traces

**Definition:**
Traces record the **flow of a single request across multiple services**, showing **how the request was processed end-to-end**.

**Characteristics:**

* Made up of **spans**, each representing a step in the request.
* Include timing info (start, end, duration).
* Span IDs are correlated using a **trace ID** across services.

**Example Trace for Order 12345:**

```
Trace ID: order-12345
  Span 1: API Gateway → Order Service (50ms)
  Span 2: Order Service → Payment Service (200ms)
  Span 3: Payment Service → Database (100ms)
  Span 4: Order Service → Inventory Service (50ms)
  Span 5: Notification Service → Email (50ms)
```

**Key point:** Traces **connect multiple services** and show the **causal path** of a single request.

---

## 4. Logs vs Traces vs Metrics — Quick Comparison

| Aspect      | Metrics                        | Logs                             | Traces                                      |
| ----------- | ------------------------------ | -------------------------------- | ------------------------------------------- |
| Granularity | Aggregated, numeric over time  | Single event at a point in time  | End-to-end request path across services     |
| Scope       | Entire system or service       | Single service or component      | Multiple services / distributed system      |
| Purpose     | Monitor health, trends, alerts | Debugging, auditing, monitoring  | Observability, latency, bottleneck analysis |
| Example     | 150 orders processed/min       | Payment failed for order 12345   | Order 12345 request spans across services   |
| Tools       | CloudWatch Metrics, Prometheus | CloudWatch Logs, ELK, OpenSearch | AWS X-Ray, OpenTelemetry, Jaeger, Zipkin    |

**Analogy:**

* **Metrics:** Thermometer — tells you system temperature (high-level health).
* **Logs:** Security camera snapshots — show what happened at specific times.
* **Traces:** CCTV video of a person’s journey — shows full end-to-end flow.

## FAQ: Metrics, Logs, and Traces

**Q1: Can we combine metrics and logs?**
Yes, metrics and logs are complementary. Logs capture **detailed events**, while metrics provide **aggregated numerical data** over time. You can derive metrics from logs by aggregating counts, averages, or other statistics (e.g., number of failed payments per minute). Tools like **CloudWatch** allow you to **correlate logs with metrics** for observability.

**Q2: Are metrics just a granular form of logs?**
Not exactly. Metrics are **numeric measurements** collected over time, often aggregated into intervals (e.g., per minute). While logs can generate metrics (e.g., counting errors from logs), metrics are usually optimized for **monitoring trends and triggering alerts**, not for capturing full event details.

**Q3: How are traces different from logs?**

* Logs show **what happened** in individual services.
* Traces show **how a single request flowed across multiple services**, connecting multiple logs and spans into a causal path.
  Think of logs as snapshots and traces as a full video of the request journey.

**Q4: Can metrics, logs, and traces be integrated?**
Absolutely. Modern observability platforms, including **AWS CloudWatch ServiceLens**, integrate all three:

* Metrics monitor overall system health.
* Logs provide detailed event context.
* Traces show request-level flow across services.

**Q5: Can we publish metrics for every single event?**
You can, but it’s often not practical. Publishing metrics for every event can generate high cardinality and increase storage/cost. Usually, events are **aggregated** (e.g., counts, sums, averages) over intervals like seconds or minutes.

**Q6: When should we use logs vs metrics vs traces?**

* **Metrics:** For monitoring system performance and alerting.
* **Logs:** For debugging, auditing, and investigating specific events.
* **Traces:** For understanding request flows and pinpointing latency or failures across services.

**Q7: Can a single observability tool handle all three?**
Yes. For AWS, **CloudWatch ServiceLens** combines metrics, logs, and X-Ray traces to provide **end-to-end visibility** of your applications. Other platforms like Datadog, New Relic, and OpenTelemetry-based solutions offer similar capabilities.
