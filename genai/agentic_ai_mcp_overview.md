# Switching from Static Rule Workflows to Dynamic AI Agent-Based Workflows: How LLMs, Schemas (Pydantic!), and MCP Transform Workflows

When we think of automation, the default notion is often a **rule-based workflow**:

* If *X* happens, perform *Y*.
* Then run *Z*, and stop when complete.

These rigid flows serve well for predictable pipelines—like ETL tasks, CI/CD jobs, or static chatbots. But what about workflows that are uncertain, dynamic, or context-dependent? That’s where **agents powered by LLMs** shine.


## AI Agent-Powered Workflows

Dynamic workflows involve **Agents, LLMs, MCP, Knowledge Bases, and Tasks**.

**Flow Example**:
User → Agent → Plan generated by LLM (validated via Pydantic) → Loop(MCP Client or Knowledge Base → MCP Server or Vector DB → Result sent back to LLM) → LLM Final Result → Agent → User

This allows agents to dynamically decide **what tool to call**, **how many steps are needed**, and **when the task is truly complete**.

---

## 🔹 What Is an Agent?

An **Agent** is an adaptive system that uses a **Large Language Model (LLM)** to dynamically plan and execute steps, unlike hardcoded logic.

1. **Input**

   * **A goal or question (from the user):**
     *“What are the top 5 open issues in the `my-org/my-repo` GitHub repository?”*
   * **Memory/context:** Conversation history, past tool calls, prior results.

2. **Planning via LLM**

   * The agent asks the model, *“Given this goal and memory, what should we do next?”*
   * The LLM returns a **structured plan** in JSON:

     ```json
     {
       "status": "in_progress",
       "action": "fetch_github_issues",
       "parameters": {"repo": "my-org/my-repo", "limit": 5}
     }
     ```

3. **Execution by Runtime**

   * The runtime parses the action, invokes tools or APIs (e.g., RAG with a knowledge base, or an MCP server for GitHub), and returns results to the LLM.

4. **Iteration Loop**

   * LLM reflects on results: continue (`status = in_progress`) or complete (`status = done` + `final_answer`).

This dynamic flexibility is showcased in the [Strands Agents quickstart](https://strandsagents.com/latest/documentation/docs/user-guide/quickstart/), [LangGraph agents](https://langchain-ai.github.io/langgraph/agents/agents), and Anthropic’s [guide to building effective agents](https://www.anthropic.com/engineering/building-effective-agents).


## Agent vs. Rule-Based Workflow

| Feature              | Rule-Based Workflow          | Agentic Workflow (LLM-Driven)         |
| -------------------- | ---------------------------- | ------------------------------------- |
| Workflow Definition  | Predefined and rigid         | Dynamic and planned per task          |
| Flexibility          | Low (predictable paths only) | High (LLM chooses actions and path)   |
| Handling Uncertainty | Hard-coded logic             | Natural fit via reasoning             |
| Task Completion      | Known endpoint               | LLM decides when to stop (fuzzy)      |
| Examples             | ETL, scripted automation     | Research assistants, agentic copilots |



## The Power of Schema-Specific Output (with **Pydantic**)

A key enabler for agent reliability is **structured output**. Instead of ambiguous prose, the LLM must conform to a **Pydantic schema**, ensuring runtime validation and safe execution.

### Example: Pydantic plan schema

```python
from pydantic import BaseModel, Field
from typing import Literal, Dict, Any, Optional

class Plan(BaseModel):
    status: Literal["in_progress", "done"]
    action: Optional[str] = Field(None, description="Tool to invoke when in_progress")
    parameters: Dict[str, Any] = {}
    final_answer: Optional[str] = None
```

When the LLM returns JSON:

```python
plan = Plan.model_validate_json(llm_output_json)
```

* If validation fails → **re-prompt** the LLM.
* If validation succeeds → **dispatch `plan.action`** with `plan.parameters`.

This ensures the plan is **machine-readable and type-safe**, and frameworks like **LangGraph** and **Strands** rely on this pattern.

---

## 🔹 The Fuzzy Judgment: How Does the LLM Know When It’s Done?

Unlike rule-based flows, agents rely on the LLM’s *internal reasoning*:

* **Runtime constraints** enforce `status = "done"` vs `status = "in_progress"`.
* **Prompt rules**: Only mark `done` if the request is satisfied.
* **Pydantic validation** ensures output correctness but not judgment correctness.

Completion is **probabilistic**, balancing flexibility with structured validation.


## Example in Action

User: *“What are the top 5 open issues in the `my-org/my-repo` GitHub repository?”*

1. **LLM Plan (validated by Pydantic)**

```json
{
  "status": "in_progress",
  "action": "fetch_github_issues",
  "parameters": {"repo": "my-org/my-repo", "limit": 5}
}
```

2. **Tool Result (via MCP GitHub Server)**

```json
[
  {"id": 101, "title": "Fix login timeout bug"},
  {"id": 102, "title": "Improve error logging"},
  {"id": 103, "title": "Add OAuth2 support"},
  {"id": 104, "title": "Update docs for API v2"},
  {"id": 105, "title": "Optimize database queries"}
]
```

3. **LLM Reflection (validated by Pydantic)**

```json
{
  "status": "done",
  "final_answer": "Here are the top 5 open issues in my-org/my-repo:\n1. Fix login timeout bug\n2. Improve error logging\n3. Add OAuth2 support\n4. Update docs for API v2\n5. Optimize database queries"
}
```

The agent stops because the **LLM set `status` to `done`** and the Pydantic model accepted the output.

> *Note:* If instead of GitHub, the task required summarizing internal design docs, the agent might call a **RAG-enabled knowledge base** rather than an MCP server. This demonstrates flexibility in tool selection.


## Introducing the Model Context Protocol (MCP)

The **Model Context Protocol (MCP)** is a universal standard for connecting LLMs to external data sources and tools securely and dynamically. It solves the **N×M integration problem**: every model previously needed a custom adapter for every tool.

### MCP Architecture Overview

1. **Agent** – LLM-driven reasoning loop that generates structured plans.
2. **MCP Host** – Runtime environment running agents (e.g., IDE plugin, chat app, orchestrator).
3. **MCP Client** – Bridge that speaks MCP protocol, discovers servers, and routes tool calls.
4. **MCP Server** – Tool or data integration (e.g., GitHub, Jira, Snowflake) exposing tools and schemas to clients.

**Flow Example:**
LLM → MCP Client → MCP Server → Results → LLM → Agent → User

MCP allows agents to **scale across systems without rewriting integrations**, with strict schema validation and secure communication.



## Frameworks for Building Agents

Several ecosystems help developers **build, orchestrate, and scale agents**:

* **[LangGraph](https://langchain-ai.github.io/langgraph/agents/agents/)** – Graph-based orchestration with memory, retries, and structured output.
* **[Strands Agents](https://strandsagents.com/latest/documentation/docs/user-guide/quickstart/)** – Schema-first planning and structured responses.
* **[LangFlow](https://www.langflow.org/)** – Visual, no-code/low-code interface for chaining agents and tools.
* **[FlowWise](https://flowwiseai.com/)** – Visual workflow builder for LLM-powered agents.
* **[n8n](https://n8n.io/)** – General automation/orchestration platform extended for agentic flows.
* **Amazon Bedrock Agents & Bedrock Agent Core** – Enterprise-grade agents with orchestration, guardrails, and retrieval integration.

Framework focus varies: LangGraph/Strands lean developer-first (structured Pydantic plans), LangFlow/FlowWise/n8n lean visual/workflow-first, and Bedrock emphasizes enterprise-scale deployment.



## Frameworks for MCP

MCP ecosystem components:

* **MCP Servers** – Node.js/Python/Go tools exposing resources (GitHub, Jira, file systems).
* **MCP Clients** – Embedded in agent runtime, handling discovery, schema validation, and communication.
* **MCP Hosts** – Run agents + MCP client; examples include IDE plugins, LangGraph orchestration layers, Bedrock orchestrators.


## Why This Matters

Agents that combine **LLM reasoning + Pydantic validation + MCP connectivity** offer:

* **Adaptive workflows**: dynamically plan multi-step work.
* **Safe execution**: schema-validated outputs prevent misfires.
* **Interoperability**: connect to any MCP server without custom glue code.
* **Composable architecture**: mix-and-match frameworks, servers, and tools seamlessly.

They transform automation from **rigid rule execution** to **dynamic, human-like problem-solving workflows**.
